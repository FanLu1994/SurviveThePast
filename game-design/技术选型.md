# 《穿越失败》技术选型

## 一、目标

- 支持桌面端与移动端浏览器
- 无账号、无后端、可静态部署
- 支持结构化剧情、证据推理和本地存档
- 允许历史关卡独立制作、审校和加载
- 保持叙事逻辑与页面显示分离

## 二、最终方案

采用 React + TypeScript + Vite，并实现轻量叙事领域层。

### 前端

- React：场景、对话、证据板、设置和结算页面
- TypeScript：剧情节点、条件、效果、证据、身份与存档类型
- Vite：开发环境和静态生产构建
- Zustand：管理单局状态、设置和局外图鉴
- Zod：校验关卡内容结构和引用关系
- CSS Modules：组件样式
- 全局设计令牌：管理颜色、字体、间距和关卡主题

### 存档

- IndexedDB 保存局内进度、设置和史料图鉴
- 每份存档包含 `schemaVersion`
- 版本升级时执行存档迁移
- 浏览器存储不可用时允许临时游玩，并明确提示无法保存

### 静态资源

- 图片与音频按关卡组织
- 进入对应关卡后按需加载
- 媒体资源缺失时保留文本流程
- 首版使用浏览器原生音频能力

## 三、叙事领域层

叙事领域层负责：

- 读取当前剧情节点
- 判断选项条件
- 执行选项效果
- 修改局内状态
- 记录证据
- 更新玩家假设
- 推进到下一节点
- 判定结局与图鉴解锁

该层不依赖 React。

## 四、内容组织

每个历史关卡作为独立内容包，包含：

- 关卡元信息
- 场景节点
- 人物资料
- 身份池
- 证据定义
- 条件与效果
- 结局
- 史料来源

构建前检查：

- 节点编号是否重复
- 节点引用是否存在
- 条件与效果字段是否合法
- 来源编号是否存在
- 是否存在不可达节点
- 是否至少存在一个可达结局

校验失败时阻止发布，并报告具体关卡、节点和字段。

## 五、建议代码结构

```text
src/
  game/
    types.ts
    engine.ts
    content-schema.ts
    scenario-loader.ts
  stores/
    game-store.ts
  storage/
    save-repository.ts
  features/
    play/
    evidence/
    archive/
    settings/
  content/
    levels/
      late-han/
      northern-song/
      early-republic/
```

- `src/game/types.ts`：领域类型与稳定接口
- `src/game/engine.ts`：条件判断、效果执行和节点推进
- `src/game/content-schema.ts`：关卡内容结构校验
- `src/game/scenario-loader.ts`：加载和索引关卡包
- `src/stores/game-store.ts`：局内状态与玩家操作
- `src/storage/save-repository.ts`：本地存档读写和迁移
- `src/features/play/`：舞台、对话、选择和状态界面
- `src/features/evidence/`：证据板与假设提交
- `src/features/archive/`：史料图鉴与来源展示
- `src/content/levels/`：正式关卡内容

## 六、异常处理

- 媒体资源缺失时继续文本流程
- 剧情节点无法推进时显示明确错误并保留存档
- 存储不可用时提示本次进度无法保存
- 存档无法迁移时保留局外图鉴，安全放弃不兼容的当前局
- 不静默覆盖或删除玩家存档

## 七、部署

游戏构建为纯静态站点，可部署到 Cloudflare Pages、Vercel 或任意对象存储与 CDN。

## 八、未选方案

### Ink + inkjs + React

分支剧情脚本可读性较好，但证据关系、史料元数据和 React 状态之间需要额外桥接，不适合当前以结构化推理为核心的玩法。

### Godot Web

适合复杂场景和 2D 探索，但首版在网页体积、移动浏览器加载、文本排版和可访问性方面成本更高。

- 人工完整通关验证
